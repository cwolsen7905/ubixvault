# uBixVault v1.6.0: integrated storage, no database required

uBixVault can now keep its own data. Start it with `-storage raft` (or
`storage.type=raft` in the Helm chart) and three replicas form a cluster that
replicates every write to a majority before acknowledging it. There is no
MySQL to provision, patch, back up separately or lose.

## What you get

- **A replicated store with no external dependency.** Three replicas, each with
  its own volume, tolerate the loss of any one: the cluster re-elects in seconds
  and no acknowledged write is lost. Two replicas down means no quorum, so
  writes fail rather than diverge.
- **The same operations.** Auto-unseal, snapshots, the backup CronJob, the
  rolling upgrade and the `operator` CLI all work as before; there is a new
  `operator raft` group for peers, join tokens, snapshots and recovery, with
  Vault-compatible shapes where they exist.
- **Joining is explicit.** A new replica joins with a single-use, short-lived
  token and the cluster's CA is pinned; peer traffic is mutually authenticated
  TLS on the existing cluster port.
- **A way over from MySQL.** One maintenance window: export the ciphertext
  from the database, restore it into the first replica's volume, start with the
  same unseal key, join the others. Nothing above storage changes, so no token,
  lease or secret is invalidated, and the rollback is a snapshot back into the
  database. The procedure is rehearsed in CI on every change, in both
  directions.

## How it was tested

- A Jepsen-style checker runs concurrent clients against a three-node cluster
  under random crashes, partitions and leadership changes every night, checking
  each key as a linearizable register and that no acknowledged write is lost.
- On Kubernetes (kind): the leader's node frozen, the leader partitioned from
  the majority, the whole cluster restarted, and a replica's volume wiped, all
  under a client writing without retries. TODO: figures from the first run

- A replica that comes back on a wiped volume refuses to found a second cluster

## What to know before you use it

- It is a new storage engine. MySQL remains supported and remains the default
  for existing deployments; migrate when you have a window and a recent
  snapshot, and keep the database for the soak period.
- Run **3 or 5** replicas (odd). Two is refused by the chart.
- Use block storage with real `fsync`, not NFS/SMB.
- Auto-unseal is the practical mode: a sealed replica does not vote, so a full
  restart under Shamir shares needs operators to unseal a quorum first.
- It is not Vault's integrated storage byte for byte: a few response shapes
  differ (the chart README and `docs/design/raft-storage.md` list them), and
  autopilot is membership and leader only.

## Upgrading

Existing MySQL and file deployments need nothing. To adopt integrated storage
see **Migrating from MySQL to Raft** in `docs/DEPLOYMENT.md`; for a new
cluster, the chart README's "Deploying with Raft storage".
