# uBixVault v1.6.0: integrated storage (experimental), and where we stand

uBixVault is a lightweight, open, Vault-API-compatible secrets manager: one small
Go binary, no plugin processes, Vault's request shapes so the `vault` CLI and
External Secrets Operator work unmodified. 1.6.0 adds the piece that most
separated it from Vault in a cluster: it can keep its own data.

Start it with `-storage raft` (or `storage.type=raft` in the Helm chart) and
three replicas form a cluster that replicates every write to a majority before
acknowledging it. No MySQL to provision, patch or lose. **It ships as
experimental**: we run it on our own dev and then prod first, and the label
comes off after that soak.

## What you get

- **A replicated store with no external dependency.** Each replica has its own
  volume; any one can be lost. Two down means no quorum, so writes fail rather
  than diverge.
- **The same operations.** Auto-unseal, snapshots, the backup CronJob and the
  rolling upgrade work as before; `operator raft` adds peers, join tokens,
  snapshots and recovery, and the raft endpoints use Vault's response envelope
  so `vault operator raft list-peers` works.
- **Explicit joining.** A new replica joins with a single-use, short-lived token
  against a pinned CA; peer traffic is mutually authenticated TLS.
- **A way over from MySQL.** One maintenance window: export the ciphertext from
  the database, restore it into the first replica's volume, start with the same
  unseal key, join the others. Nothing above storage changes, so no token,
  lease or secret is invalidated, and rollback is a snapshot back into the
  database.

## What we measured

On kind, three replicas, a client writing every 100 ms through the Service with
no retries, and every acknowledged write checked afterwards:

| Event | Result (range over three runs) |
| --- | --- |
| Leader's node frozen | another leader in **6-7 s** |
| Leader partitioned from the majority | new leader in **11-17 s**; the isolated leader answered **503** to every write |
| Acknowledged writes (every run) | **all read back** from the Service and every replica (93/93, 85/85, 71/71 at that stage) |
| Whole cluster restarted (PVCs kept, auto-unseal) | serving again in **18 s**, nothing lost |
| One replica's volume wiped (`-2`) | back as a voter in **19 s** |
| Pod `-0` on a wiped volume | **refuses to found a second cluster** under its old identity; given a join token it rejoins with the configuration intact |

The same write, read and list load through the same Service, MariaDB against
Raft (zero errors; the Raft term did not move, so the 500 ms leader lease held):

| Load | MariaDB p50 / p99 ms | Raft p50 / p99 ms |
| --- | --- | --- |
| write, 1 client | 4.5 / 6.2 | 4.5 / 6.7 |
| write, 8 clients | 13.4 / 24.2 | 14.9 / 30.9 |
| read, 8 clients | 7.9 / 18.3 | 5.1 / 28.8 |
| list 100 keys, 4 clients | 4.6 / 8.9 | 3.5 / 6.9 |

Writes cost about what a MySQL round trip does. These are CI-VM numbers: a
regression baseline, not capacity planning.

The MySQL-to-Raft migration was rehearsed end to end both on the same Helm
release (`--cascade=orphan`) and as a parallel release: 48 of 48 entries
present, 33-35 s from freezing the old release to the first read served by
Raft, and a rollback (41-46 s) that brought MySQL back with a write made on
Raft intact.

The tests earned their keep: the chaos run found that a bootstrapped node's
address was stored as a pod IP rather than its DNS name, and a Jepsen-style
checker found that a newly elected leader could answer a consistent read from a
state machine that had not applied the previous leader's last entries. Both are
fixed in 1.6.0.

Jepsen-style testing, stated plainly: three 2-minute runs of about 100,000
operations each found no violation, but the checker could not decide every
window of the history (it gave up on its step budget on all three keys), so
this is **not a proof** of linearizability. Widening that coverage is open work.

## What to know before you use it

- It is a **new storage engine and it is experimental.** MySQL and file storage
  are unchanged and remain the default; migrate when you have a window and a
  recent snapshot, and keep the database for the soak.
- uBixVault has had **no independent security audit.** That is still the open
  milestone.
- Run **3 or 5** replicas (the chart refuses an even number). Use block storage
  with real `fsync`, not NFS/SMB.
- Auto-unseal is the practical mode: a sealed replica does not vote, so a full
  restart under Shamir shares needs operators to unseal a quorum first.
- It is not Vault's integrated storage byte for byte: autopilot is membership
  and leader only, and a few shapes differ (`docs/design/raft-storage.md`).
- The top-level keys of the raft `configuration` and `autopilot/state` responses
  are deprecated in favour of `data`.

## Upgrading

Existing MySQL and file deployments need nothing. To adopt integrated storage
see **Migrating from MySQL to Raft** in `docs/DEPLOYMENT.md`; for a new
cluster, the chart README's "Deploying with Raft storage".

Full changelog: CHANGELOG.md. Design and measurements:
