# uBixVault v1.7.0: hand out role administration without handing out root

uBixVault is a lightweight, open, Vault-API-compatible secrets manager: one small
Go binary, no plugin processes, and Vault's request shapes, so the `vault` CLI
and External Secrets Operator work unmodified. 1.7.0 is about **delegation**.
A platform team can now let other people manage login roles while still
controlling what those roles hand out. Before this release, anyone who could
write a role could make themselves root.

## What changed

- **Root comes only from the key holders.** A root token now comes only from
  initialization, from `generate-root` (a quorum of unseal key shares), or from
  another root token. Before 1.7.0, an auth role could list the `root` policy,
  and logging in through that role gave a root token. Every auth method (JWT,
  Kubernetes, AppRole, userpass, cert, LDAP groups) now refuses `root` when a
  role is written, and refuses it again at login. Only a root token can create
  another root token through `auth/token/create`; `sudo` is no longer enough.
  This matches Vault.
- **Parameter limits in ACL policies.** Policies accept `allowed_parameters`,
  `denied_parameters` and `required_parameters`, in JSON and HCL, with Vault's
  semantics. A policy can let someone write a role but only with certain
  values. The limits come from the most specific matching path, so a broader
  grant such as `auth/*` doesn't lift them.
- **Partial role updates everywhere.** On JWT, Kubernetes, AppRole and cert
  roles and on userpass users, a write to an existing role changes only the
  fields it sends, as in Vault. Every method accepts `token_policies`, and list
  fields accept either a list or a comma-separated string. Concurrent updates
  to the same role are applied one at a time, so neither is lost.
- **`sys/capabilities-self` and `sys/capabilities`.** A token can ask what it
  may do on a set of paths, so `vault token capabilities` works. The answer is
  computed the same way as the real permission check, and a test holds them
  together, including for identity and templated policies.

## Example: a role administrator who can't escalate

```hcl
# Manage JWT and Kubernetes login roles, but only hand out app-* policies.
path "auth/jwt/role/*" {
  capabilities = ["create", "update", "read", "list"]
  allowed_parameters = {
    "token_policies"  = ["app-*"]
    "role_type"       = []
    "user_claim"      = []
    "bound_audiences" = []
    "bound_claims"    = []
    "token_ttl"       = []
    "token_max_ttl"   = []
  }
}

path "auth/kubernetes/role/*" {
  capabilities = ["create", "update", "read", "list"]
  allowed_parameters = {
    "token_policies"                   = ["app-*"]
    "bound_service_account_names"      = []
    "bound_service_account_namespaces" = []
    "token_ttl"                        = []
    "token_max_ttl"                    = []
  }
}
```

A holder of this policy can create a JWT role that grants `["app-web", "app-db"]`.
A request is refused with `403` in each of these cases:

- it grants `admin`
- it mixes `app-web` with anything outside `app-*`
- it uses the older `policies` field, which this policy doesn't list

Every element of a list must be allowed. `root` is refused whatever the policy
says. Partial updates mean a later `token_ttl=2h` write changes just the TTL.

## What to know before you upgrade

- **A role that lists `root` stops working.** Logins through it now fail.
  Remove `root` from the role. Writing an ACL policy named `root` is also
  refused.
- **Role writes no longer replace the whole role.** If you relied on a write
  clearing the fields it left out, send them empty instead
  (`"bound_claims": {}`).
- Limits apply to the JSON body of `POST`/`PUT` writes. Limits on `GET` query
  parameters are not supported. `required_parameters` checks that a parameter
  is present, as Vault does, so an empty value such as `{}` passes.
- uBixVault has had **no independent security audit**. That is still the open
  milestone. Raft storage remains **experimental**.

## Upgrading

Replace the binary or image (chart 0.1.23, appVersion 1.7.0). There is no
storage migration. **Before** you roll out, while still on 1.6.0, find any role
that lists `root`. 1.6.0 reports a role's policies as `policies`, and 1.7.0 as
`token_policies`, so the check reads both. Matching ignores case and
surrounding spaces, the same way 1.7.0 matches. A role that can't be listed or
read is reported as an error rather than skipped:

```bash
#!/usr/bin/env bash
# Needs a token that can list and read the roles. Keep only the auth methods
# you have enabled (default mount paths shown). Any failure is reported, so
# no output and exit status 0 means no role lists root.
methods=(jwt/role kubernetes/role approle/role cert/certs userpass/users ldap/groups)
status=0
for dir in "${methods[@]}"; do
  if ! names=$(vault list -format=json "auth/$dir" 2>&1); then
    [[ $names == *"No value found"* ]] && continue   # no roles here
    echo "ERROR: cannot list auth/$dir: $names" >&2; status=1; continue
  fi
  while IFS= read -r name; do
    if ! role=$(vault read -format=json "auth/$dir/$name" 2>&1); then
      echo "ERROR: cannot read auth/$dir/$name: $role" >&2; status=1; continue
    fi
    if jq -e '[.data.token_policies, .data.policies] | flatten
              | map(select(. != null) | ascii_downcase | gsub("^\\s+|\\s+$"; ""))
              | index("root")' >/dev/null <<<"$role"; then
      echo "auth/$dir/$name lists root"; status=1
    fi
  done < <(jq -r '.[]?' <<<"$names")
done
exit $status
```
